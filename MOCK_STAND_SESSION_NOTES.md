Vladimir провёл первый пилотный тест с CPO. По итогам — 4 пункта запроса,

## 1. Профиль компании — новый первый шаг тура

**Запрос:** взять со старого standalone-концепта (`web_onboarding`,
https://self-onboarding-production.up.railway.app/) шаг: название компании,
сфера деятельности, роль администратора.

**Реализация:**
- `models.py`: `Organization` получил `company_name`, `industry`, `admin_role`
  (все `nullable=True`, изначально `None`).
- `main.py`: `GET/POST "/"` — раньше `/` был просто редиректом/заглушкой,
  теперь настоящая форма. `POST` валидирует (непустое имя, industry/admin_role
  из фиксированного списка) через `redirect_with_error()`.
- Справочники в `main.py`: `INDUSTRIES` (7 сфер: retail/food/it/manuf/edu/
  health/other), `ADMIN_ROLES` (owner/hr/lead/fin) — тексты портированы из
  `web_onboarding/static/i18n.js`, не придуманы заново.
- `templates/home.html` — сама форма. Маркер `data-company-set="1"`
  (скрытый div) рендерится, когда все три поля заполнены — на нём завязан
  `check()` шага тура.
- `static/tour/steps.js` — новый первый шаг `id: 'company'`, `route: '/'`,
  `inputSelector: 'input[name="company_name"]'`.
- Лого VERIFIX в `base.html` обёрнуто в `<a href="/">` — нужно было, чтобы у
  `renderNavGuide()` был реальный `<a>` для подсветки (раньше в меню ссылки
  на `/` не было вообще).

**Важный найденный и исправленный баг (см. §5 ниже, п.1):** `onRoute()` в
`verifix-tour.js` матчил через `indexOf()` — а `/` это подстрока АБСОЛЮТНО
любого пути, так что шаг «company» считал себя «на своей странице» везде.
Пофикшено точным сравнением `location.pathname === '/'` для этого частного
случая.

## 2. Типовые подразделения/должности по сфере

**Запрос:** раз пользователь указывает сферу — предлагать типовые
подразделения/должности (см. тот же старый концепт).

**Реализация:**
- `main.py`: словари `DIVISION_SUGGESTIONS` / `POSITION_SUGGESTIONS`
  (ключ — код сферы), тоже портированы из `web_onboarding/static/app.js`.
- `division_list()` / `job_list()` (GET-хендлеры) считают `suggestions`:
  список сферы минус уже существующие (по имени, case-insensitive).
- `templates/division_list.html` / `job_list.html` — чипы `.chip`. Каждый
  чип — отдельная мини-форма (`<form>` с hidden `name=<suggestion>`),
  клик = мгновенное создание записи (не просто подстановка в поле ввода).

## 3. Двухпанельный layout + постоянная панель «результат»

**Запрос и решение по архитектуре (важно для QA — это не то же самое, что
обычный редизайн):** верхняя навигация остаётся полностью функциональной
(клики по Кадры/Посещения/... не убраны). Экран делится на 2 колонки:
- **Левая** (`~50%`, класс `.content-full`) — тот же контент, что был на
  каждой странице раньше (форма+список), просто в более узкой колонке.
- **Правая** (`~50%`, класс `.org-visual-panel`) — НОВАЯ, постоянная на
  ВСЕХ страницах (не только на страницах подразделений/сотрудников).
  Живой снепшот оргструктуры, пересчитывается на сервере при КАЖДОЙ
  загрузке страницы — поэтому правки на любом шаге видны на панели,
  независимо от того, на какую страницу вернулся пользователь.

**Реализация:**
- `main.py`: `build_org_snapshot(db, org)` — строит дерево подразделений
  (с вложенностью через уже существующий `_ordered_divisions()`) + список
  сотрудников по подразделению + список локаций с прикреплёнными
  сотрудниками + список неприкреплённых сотрудников. Подключено в
  `base_ctx()` под ключом `org_snapshot` — значит доступно на ЛЮБОЙ
  странице, использующей `base_ctx()` (это все страницы).
- `templates/base.html`: `<div class="workspace">` — flex-обёртка,
  `<main class="content-full">` + `<aside class="org-visual-panel">`.
  Панель рендерит дерево (`.ovp__division` карточки с чипами `.ovp__chip`
  сотрудников) и локации (`.ovp__location-circle`, круглые ячейки).
- **Drag-and-drop:** каждый аватар сотрудника (`.ovp__avatar[draggable]`,
  `data-employee-id`) можно перетащить на круг локации
  (`.ovp__location-circle`, `data-location-id`) или в пул
  `.ovp__unassigned-pool` (`data-location-id=""`). JS в `base.html` слушает
  `dragstart/dragover/drop`, шлёт `fetch POST` на новый эндпоинт
  `/vhr/href/employee/{id}/assign_location` (main.py), затем
  `location.reload()` (полная перезагрузка — сознательно, чтобы не рисковать
  расхождением DOM/БД при ручной правке клиента).
- **ПОБОЧНОЕ, но необходимое изменение:** в предыдущем QA-раунде
  `employee_create()` требовал ВСЕ 4 связи (включая `location_id`)
  обязательными. Это прямо противоречит новому drag-and-drop (сотрудник
  должен уметь существовать «непривязанным», чтобы прикрепление через
  панель имело смысл). **Location_id снова необязателен** при создании;
  подразделение/должность/график — остаются обязательными. Клиентский
  `required` тоже снят с `<select id="empLocation">` в `employee_list.html`.
- Панель тура (`.vtour-panel`, чек-лист прогресса) **дважды переезжала** в
  этой сессии:
  1. Сначала из правого нижнего угла (фиксированная, floating) в левый
     нижний угол — потому что правый теперь занят `.org-visual-panel`.
  2. Затем — из floating-оверлея (`position:fixed`) в настоящий элемент
     потока страницы: `<div id="tourPanelSlot">` в самом верху
     `.content-full`, сразу под топбаром (`position:sticky`). Это было
     нужно, потому что floating-версия перекрывала форму (конкретно —
     кнопку «Сохранить и продолжить» на форме компании, воспроизведено на
     скрине пользователя).
  JS: `render()` в `verifix-tour.js` теперь ищет `#tourPanelSlot` и
  вставляет туда `.vtour-panel` (`appendChild`), с фолбэком на старое
  поведение (append в `#vtour-root`), если слота на странице нет.

**Проверка ширины панели:** изначально была жёстко `width: 320px` (по факту
~15-20% экрана) — не то, что подразумевалось под «делится на 2 части».
Исправлено на `flex: 1 1 50%` для обеих колонок; `.page` (внутренний
контейнер форм) уменьшен с `max-width: 900px` до `640px`, чтобы формы не
боролись с сузившейся левой колонкой; `.field-row` получил `flex-wrap`.

## 5. Баги, найденные и исправленные в процессе (не были в запросах, всплыли по ходу)

1. **`onRoute()` ложно матчил `/`** — см. §1. Воспроизведено через jsdom
   (симуляция без браузера), подтверждено до/после фикса.
2. **`renderNavGuide()` не находил «вкладку» для ссылки-логотипа** —
   логотип не лежит внутри `.topnav__item` (это не пункт дропдауна), код
   ожидал `link.closest('.topnav__item')` и падал в фолбэк. Добавлена
   отдельная ветка для ссылок без родительской вкладки дропдауна.
3. **Панель прогресса перекрывала форму** — см. §3, дважды исправлено.
4. **Ширина панели результата не соответствовала «делится на 2 части»** —
   см. §3.

## 6. Известные компромиссы / не доделано

- Двухпанельный layout **не адаптирован под мобильные/узкие экраны** —
  на `<900px` `.org-visual-panel` просто скрывается (`display:none`),
  осознанное упрощение, не баг.
- Drag-and-drop **на предыдущий стенд (тач-устройства)** не проверялся —
  HTML5 drag-and-drop API исторически плохо работает на тач, это не
  покрыто (аналогично QA-фиксу №2 из прошлого раунда про DnD-дерево
  подразделений, там уже есть `<select>`-фолбэк; для локаций такого
  фолбэка пока НЕТ).
- Полный regression прогонялся через `curl` (все HTTP-коды, данные в БД)
  и через `jsdom`-симуляцию (JS-логика тура без реального браузера) —
  **визуальную раскладку (реальные пиксели/CSS) никто не проверял
  автоматически**, только на скринах, которые прислал Vladimir.
